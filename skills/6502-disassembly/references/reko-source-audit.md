# Three checks before trusting a 6502 decompilation

A readable listing can attach a branch to the wrong flag, hide a second entry, or label BASIC text as machine code.  The checks below recover the evidence behind those three decisions.  The linked Reko sources and tests are pinned to `b5a4afc2cb85d8a426057b895bdf6be7644cfdb2`.  The examples are independent hand calculations; they do not require Reko.

## 1. Audit the flag producer and the memory access, not just the branch

Work backward from the branch: identify the flag it consumes, find the last instruction that defines that flag on each incoming path, and check its rule against the target CPU.  For each operand access, record the effective address, CPU-visible mapping, access order, and whether a read or write is observable even if its value is unused.  An unknown mapping is a reason to keep the access, not to name a device.

**Worked NMOS 6502 example.**  At `$2000`, `A9 01 2C 00 40 F0 02` means `LDA #$01; BIT $4000; BEQ $2009`.  Suppose `$4000` is RAM containing `$C0`, and carry is initially set.  The load leaves Z clear.  `BIT` reads `$C0` once without changing A: bits 7 and 6 set N and V, the zero result of `$01 AND $C0` sets Z, and C remains set.  The branch is taken.  Change only the operand byte **in RAM** to `$C1`: N, V, A, and C are unchanged from the first outcome, but Z clears, so execution falls through to `$2007`.

**Why inspect the producer?**  The pinned [BEQ test](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/UnitTests/Arch/Mos6502/RewriterTests.cs#L108-L115) checks that the branch consumes Z.  The pinned [BIT lowering](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Arch/Mos6502/Rewriter.cs#L192-L200), however, derives an N/V/C group from the masked value and does not define Z.  Following just those definitions would leave the earlier load's Z reaching the branch.  This is a discrepancy in that lowering, not an observed result from running the decompiler.

**I/O limit.**  The same audit applies to a read-modify-write instruction.  The [memory INC lowering](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Arch/Mos6502/Rewriter.cs#L233-L241) shows one read of the operand, a computed byte, and one store; [absolute operands](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Arch/Mos6502/Rewriter.cs#L425-L426) are byte memory accesses.  For `INC $D020` on an NMOS 6510, distinguish the data read, write of the old byte, and write of the incremented byte.  With C64 I/O visible, both writes reach a device; with RAM mapped for reads and writes, the same final RAM byte does not demonstrate equivalent bus behavior.  Do not infer device effects, cycle timing, or another CPU variant's bus sequence from this lowering.

## 2. Require an incoming-edge inventory before folding blocks together

Keep the original address labels.  For a candidate sequence `P → Q`, first check that P has only that normal successor.  List Q's incoming sources under the same mapping and execution stage, including fall-through, direct branches, resolved indirect transfers, and separately evidenced entry points.  Mark any relevant unresolved dispatch.  Fold for display only if entry through P is the sole admitted route to Q; otherwise retain Q as a label or shared tail.  Preserve the address-level graph even when you fold.

**Example and counterexample.**  A setup block falls into an output block.  With no other entry in a closed region, the two can be shown in order.  If a dispatch table also sends one case directly to the output block, that case **does not run setup**.  Keep the output label and point both paths to it.  An unresolved table is not evidence of that second edge, but it precludes claiming the predecessor inventory is complete when Q remains a plausible target.

Reko's [sequence reduction](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Decompiler/Structure/StructureAnalysis.cs#L391-L408) checks the successor's predecessor count in its region graph.  The [graph builder](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Decompiler/Structure/RegionGraphBuilder.cs#L57-L102) uses the supplied procedure edges; it does not discover missing machine entries there.  The [irregular switch-entry test](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/UnitTests/Decompiler/Structure/StructureAnalysisTests.cs#L844-L875) explicitly supplies both a branch and a switch edge to the same case.  It checks reconstruction **given** the edges, not recovery of an unknown jump table.

## 3. Bound linked BASIC records before admitting a native or VM entry

Read the PRG's two-byte little-endian load address; map payload byte zero there.  At an independently justified BASIC start, walk the links using **file-backed bytes**, not zero-filled address space.  For an ordinary contiguous tokenized BASIC program, require a forward in-range link, a two-byte line number, and a zero terminator immediately before the linked address.  At that address, two zero link bytes end the chain.  Stop and report a gap on a repeated address, missing terminator, or out-of-file link; a noncanonical layout requires separate evidence, not automatic rejection as non-BASIC.  Parse `SYS` as a token in statement context, not a byte pattern inside a string or remark.  Record the computed target separately from both the end marker and the classification of any remaining bytes.

**Worked PRG, in hex:** `01 08 | 0B 08 0A 00 9E 32 30 36 31 00 | 00 00 | 60`.  The file maps at `$0801`.  Line 10, `SYS2061`, ends at `$080A`; its link points to the zero link at `$080B`.  The literal target, `$080D`, lands on the appended `$60` (`RTS`).  The checked call target admits that byte as a native entry candidate.  The tail's position alone does not.  Change just the last digit `$31` to `$32`, keeping the file length fixed: the line and end marker are still valid, but the target `$080E` is outside the supplied payload.  Do not manufacture an instruction from zero-filled RAM.  Neither variant identifies a compiler or establishes p-code; that needs an independently evidenced fetch/dispatch path and operand grammar.

At this pin, the [PRG loader](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Environments/C64/PrgLoader.cs#L47-L69) maps at the header address but starts BASIC parsing at `$0801` and indexes the first parsed line.  It is not a general entry finder for arbitrary native PRGs.  The [line reader](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Environments/C64/C64BasicReader.cs#L63-L86) stores the line **body** separately from the full record length.  The [segment builder](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/Environments/C64/PrgLoader.cs#L83-L97) adds body length to record start to choose the `code` segment start.  In the example that arithmetic gives `$0806`, inside the SYS digits, not `$080D`.  The [SYS test](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/UnitTests/Environments/C64/C64BasicRewriterTests.cs#L140-L147) checks a literal cross-architecture call using an [already constructed line](https://github.com/uxmal/reko/blob/b5a4afc2cb85d8a426057b895bdf6be7644cfdb2/src/UnitTests/Environments/C64/C64BasicRewriterTests.cs#L80-L91), not the on-disk segment boundary.
