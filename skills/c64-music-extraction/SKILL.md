# Extract and verify Commodore music

Recover the performance before transcribing it.  A chip write says what the player did; a note, a score, and an audio render answer different questions.  Keep each so a listener can tell **where a transcription or port departs from the source**.

## Choose the evidence

1. Identify the source by hash, machine, edition, video standard, chip model, subtune or screen, and entry condition.  Prefer NTSC for a new C64 example, but use the actual source edition and clock for extraction.  Preserve original media read-only.  Use authorized inputs; keep title-specific binaries, music, recordings, RAM captures, and ROMs out of the general package.
2. Find init, the first play call, and the real scheduler: raster IRQ, CIA latch, main loop, or another source.  If inside a game, track executed writes from the requested scene, not merely a table of apparent pitches.  A table misses carried flags, counter wrap, branches, reused voices, and pitch effects.  For a `.sid`, read the header **before** choosing a runner.  Do not assume `$1000`/`$1003`, one tick per frame, or a whole tune ending at the end of a requested capture interval.
3. Log an ordered stream: `init/play, call, cycle_or_order, PC, mapped_address, value`.  Separate init writes, keep repeated values, and include all writes in each call.  On the C64, verify that I/O was visible, account for the SID base(s) and any mirrors, and track writes to the scheduler as well.  On the Plus/4, preserve the full TED control writes.  A once-per-frame snapshot can miss a gate off/on, a digital sample, or a timer change.  A CPU-only trace establishes instruction order, not SID audio or wall time.
4. Derive elapsed time from measured boundaries, or from a justified cycle count and the correct clock.  Use rational time or cumulative rounding.  Record source call and local cycle separately from inferred seconds; a reported importer “milliframe” is not a CPU cycle.  Identify the loop by player control flow **and** state across its return, distinguishing intro, loop, and trailing rest.  If the state never repeats in the budget, deliver a labeled excerpt.

**When an editable tracker song is available**, decode its per-voice order lists, patterns, instrument defaults, and row overrides before comparing it with a SID.  Match exported music bytes using only documented format changes, not a shared filename.  Make a prediction independent of the audio: for example, changing a vibrato rate while keeping the pitch and note boundaries fixed should change the interval between modulation peaks.  Compare that prediction with held-pitch register writes.  Keep editor note spelling separate from MIDI octave and measured hertz.  For an example of a documented packed source format, see the [SID-Wizard SWM specification](https://github.com/anarkiwi/sid-wizard/blob/e0c6172e5876d8bd654fe3049ac44d60fd17dba7/sources/SWM-spec.src).

Do not drop tracker rows just because their note column is empty: a global speed command there can change the duration of later notes on every voice.  Check a long hold against three separate intervals: **score** (note row to key-off row), **gate** (actual SID rise to fall, possibly delayed by a hard restart), and **release tail** (measured in the mix, with the window and threshold stated).  For loops, distinguish the order pointer wrapping from the first repeated row and the first repeated attack.

### From observed writes to timed states

[`trace_states.py`](trace_states.py) reads a CSV with columns `tick,address,value` (decimal or `0x` hex).  Keep rows in bus order, including repeated stores at the same tick.  It emits half-open intervals with exact rational durations, ordered changes, SID gate transitions, and the resulting voice latches.  Unwritten latches remain unknown.  A gate is not an amplitude measurement.  Example for an observed NTSC cycle trace, where `--end-tick` is the independently established exclusive recording boundary:

```sh
python trace_states.py sid writes.csv --clock-hz 1022730 --tick-hz 1022730 --end-tick 1022730 > states.json
```

For native `x64sc`, the [VICE 3.10 dump recipe](vice-dump/README.md) takes you from a running single-SID PRG to this CSV.  It preserves the order of repeated writes and their cycle spacing, but reports register offsets, not the original CPU address or PC.  A store to a mirror is indistinguishable from a store to the base address.  The dump supplies neither the song origin nor its end.

Use cycle timestamps when the timer stops or changes.  A fixed rate in calls per second cannot recover that timing.  The [scheduler guide and worked trace](scheduler/README.md) separate timer assertion, play entry, first register write, and audible onset.  If the supplied ticks are *observed* evenly spaced fields, use the field rate for `--tick-hz` and the chip clock for `--clock-hz`.  For TED, supply the TED double clock, not the field rate, as the chip clock.  The decoder does not invent a gate or transpose a noise clock into a melody.

### C64 SID

Keep a **chip and local voice** on each event when a tracker has more than three channels.  Voice 1 on the second chip is not voice 1 on the first.  Check that the packer supports the original channel count, read the output header for chip addresses and clock, and verify overlapping notes against writes to both register blocks.  A store to `$D420` might be the second SID in one configuration or a mirror in another.  Use the read-only [chip address annotator](selection/sid_chip_map.py): `python3 selection/sid_chip_map.py input.sid 0xd400 0xd420`.  It reads only the fixed PSID v1 through v4 header, labels declared register blocks, and warns about invalid declarations.  An undeclared possible mirror stays unresolved.  Use original CPU addresses with I/O visible; a header cannot establish what device responded, and a single-SID dump that discarded chip identity cannot recover it.  If using the single-chip interpreter below, partition an address-resolved trace by the **verified** bases first, keeping the original common timestamps.  Do not merge the results by local voice number.  To check whether both chips contribute to the sound, render the same interval with both, then with each chip’s voices muted in turn.  Use a pitch distinct to one chip as the control; two voices in unison can produce one spectral peak.  Report a host’s left/right assignment as a rendering choice, not as historical hardware wiring.  The strict PSID writer later in this guide remains single-chip.

A standard SID at `$D400` has three voices spaced seven bytes apart.  Combine each voice’s frequency low/high bytes and use `Hz = word × SID_clock_Hz / 2^24`.  `oscillator_hz` is the nominal free-running rate for the frequency word, not necessarily the fundamental heard in the mix.  The interpreter reports the individual waveform-select bits, TEST, hard sync, and ring-modulation request alongside the raw control byte.  When using hard sync or ring modulation, the wired modulation source is voice 3 for voice 1, voice 1 for voice 2, and voice 2 for voice 3.  A requested bit is not a measurement of audible modulation.  To test triangle ring modulation, compare two renders that differ only in the ring bit, keeping the source oscillator running but inaudible on its own.  Strong spectral lines near the sum and difference of the oscillator rates can appear without a second attack.  Do not transcribe those lines as a chord; preserve the modulator settings or the native audio for timbre.  Retain pulse width, ADSR, filter routing, cutoff, resonance, and master volume as appropriate.  The trace interpreter’s `filter` field reports the 11-bit cutoff **word** (`high << 3 | low & 7`), resonance, selected inputs, response modes, and the voice-3 dry-path disconnect.  A missing write is unknown; an empty list means a known empty selection.  Bit 7 of `$D418` disconnects voice 3 from the unfiltered mix, but does not disable its path through the filter if `$D417` routes it there.  The word is not a model-independent cutoff in hertz.  [Three Doors](examples/three-doors/README.md) is a playable demonstration: switching only the signal path makes one held note audible, then quiet again.  A gate falling starts release; it is not immediate silence.  Pitch writes during a held gate may be vibrato, slides, or arpeggiation rather than attacks.  A selected noise waveform or volume-register sample is not automatically a pitched note.  Preserve the actual writes even if the score simplifies them.  [Half Rate](examples/half-rate/README.md) demonstrates an audible tone with no oscillator notes: on the tested 6581 emulator, alternating two master-volume levels at about 999 writes per second produced a 499.5 Hz line.  Repeating one level at the same rate did not.  Preserve timed volume samples or PCM rather than adding a fictitious note to the MIDI.  To distinguish sampled audio from a fade, repeat the same passage with only the low volume nibble held at a **nonzero** constant.  Preserve write times and upper filter bits, and check waveform and gate history.  Muting the entire chip proves neither explanation.

[ChiptuneSAK](https://github.com/c64cryptoboy/ChiptuneSAK) offers an optional read-only starting point for supported C64 SID players.  With its dependencies available, create a fresh `SID()` for each interpretation.  `set_options(sid_in_filename=..., subtune=0, seconds=..., always_include_freq=True, assert_gate_on_new_note=False, gcf_row_reduce=False)` followed by `capture()` yields call-indexed rows in `dump.rows`; use `row.play_call_num` and `row.chips[0].channels[voice]`.  A `None` delta means unchanged, not off.  These rows are **not** the ordered store log.  The [ordered-store example](examples/ordered-capture/README.md) includes a dependency-free CSV and an optional ChiptuneSAK call hook for the original shipped tune.  Its gate-before-pitch control leaves the call-end registers unchanged but changes the order of writes to the chip.  Compare suspect inferred notes with actual frequency words and gate edges.  A new pitch tolerance can change the number of inferred notes without changing a single store.  For dependency versions, see the [reviewed source](https://github.com/c64cryptoboy/ChiptuneSAK/tree/8759135b5c9c26dc9da155b006c575243ba5304a).  Use a full machine or a qualified excerpt when the importer cannot model an IRQ, banks, timer changes, or samples.

### Plus/4 TED

TED is not a two-voice SID.  Collect `$FF0E` through `$FF12` on a Plus/4.  For the first tone, use `FF0E | ((FF12 & 3) << 8)`; for the second, use `FF0F | ((FF10 & 3) << 8)` (symbols denote register **values**).  `$FF12` also carries non-audio bits.  `$FF11` holds shared volume in the low nibble, first/second tone enables in bits 4/5, noise in bit 6, and digital mode in bit 7.  In normal mode the second oscillator supplies noise when `(control & 0x60) == 0x40`; it is not an independent third pitched voice.  Distinguish phase resets, digital volume playback, muted assignments, and held tones.  Do not manufacture a note for every reload.

For a PAL model using the 1,773,447 Hz double clock, the ordinary tone calculation is `Hz = 1773447 / (16 × (1024 - ((word + 1) & 1023)))`.  `$3FF` wraps the reload; `$3FE` is special constant-level behavior in the VICE model, not that formula’s highest musical note.  Use edition-specific clocks and observed control state; do not apply that PAL constant to an NTSC recording.  For a TED-to-SID arrangement, map the **sounding pitch, durations, rests, noise behavior, and controls**, then write a C64 player for the chosen clock; never reinterpret TED words as SID words or package the TED routine unchanged.  Disclose differences in noise, phase, envelopes, volume, and filtering.

## Derive MIDI and a readable score

For an editable SID transcription, deliver **SMF Type 1**, with a separate named track and independent MIDI channel per SID voice, including unison or initially silent voices.  Name the chip and local voice on multi-SID tunes.  Put global tempo on a conductor track, keep pitch bends with the voice they affect, and reopen the actual file to check track identities.  A single track carrying three channels is not three editable tracks.  Preserve hardware provenance if noise needs a separate audition proxy.

Maintain a voice-event ledger: source identifier, start call, exclusive end, lane, mode, base pitch, held-pitch changes, and attack evidence.  Preserve explicit same-key reattacks; do not split held notes merely to notate vibrato.  Provision independent MIDI channels for simultaneous bends, specify bend range (RPN 0), and state the tuning assumption.  Mark kit-note/noise proxies as editorial.  Preserve intro silence, the loop seam, and the final rest.  Emit explicit note-offs; round absolute event positions on the tempo map, rather than independently rounding each duration.

- **Quick sketch:** `SID().to_rchirp(filename, subtune=0, seconds=N)` → `r.to_chirp()` → `MIDI().to_file(chirp, 'sketch.mid')`.  Gate heuristics, trimmed lead-in, inferred tempo, and quantization can alter events and durations.  Inspect the exported MIDI, not just its input.  In the supplied example, automatic Chirp quantization retained all four pitches but shortened each 11-field gate to 7.5 fields on the chosen grid.
- **Gate-timed example:** `python3 -B examples/glass_steps_midi.py one-loop.mid` executes the supplied SID via ChiptuneSAK and projects its gate rows using a known NTSC VBI scheduler.  `python3 -B tests/check_midi.py one-loop.mid` reopens the SMF and checks eight edges, four pitches, elapsed time, and the last rest.  Requires ChiptuneSAK and `mido`, not for TED or arbitrary SIDs.  It preserves gates, not oscillator phase, filter response, or ADSR audio.
- **Score:** work on a **copy** of the verified performance MIDI.  Pick meter, pickup, beat grid, ties, and clefs from phrasing, not interrupt frequency.  Split concurrent pitches into separate voices before quantization; do not erase polyphony to satisfy an exporter.  A practical ChiptuneSAK route for already split voices is `MIDI().to_chirp('copy.mid', quantization='32')`, set the evidenced time/key signatures, then `Lilypond().to_file(chirp.to_mchirp(), 'score.ly', format='song')`.  `32` is an example grid, not a default analytical conclusion.  Engrave with `lilypond -o score score.ly`.  Check bar totals, reattacks, leading/trailing rests, page breaks, and ties across bars against the unquantized ledger.  Disclose bends, noise, and other effects omitted for legibility.  A `.ly` file is source, not a verified PDF.
- **Fidelity:** compare source parser, actual register performance, and separately parsed MIDI events by voice and time.  Report maximum pitch, boundary, and duration errors and any unmatched events, with a deliberate negative such as shifting a reattack by a field.  When claiming *audio* similarity, render both sides under identified engines/models, preserve alignment and untrimmed originals, and listen or measure pitch, onsets, rests, modulation, and loop length.  State which checks were auditory, measured, or not done.  Equal note names and nonzero WAV energy do not establish equal sound.

The [performance MIDI writer](performance/README.md) turns explicit timed voice spans and held pitch changes into a playable MIDI.  It includes a short original tune, source ledger, and independent event parser; it does not infer gates from pitch alone.

### Distinguish a SID attack from a register update

Keep ordered cycle timestamps, not just the last register values in each player call.  A low-byte write followed by a high-byte write can briefly produce a third frequency word.  Preserve that word in the trace; before assigning it a MIDI note, check how long it persisted, gate state, and whether an isolated native render has a separate audible attack.  Likewise, alternating triangle and noise on one held gate is a timbre change, not by itself a reason to retrigger a melodic note and a drum every time.  A tiny MIDI note can still trigger a long sampled release.  Compare the **rendered** result against the native solo before choosing a percussion or expression proxy.  There is no universal minimum duration for a real note.

For a fast cyclic pitch figure, distinguish the number of distinct pitches, the number of timed steps, and the number of gate attacks.  For example, three pitches can cycle over five equal updates without forming either five attacks or a triplet.  Where available, match the executed player command or pitch-table entries to the timed writes.  Follow the oscillator **after gate-off**: an audible release may keep cycling rather than resting or holding the last gated pitch.  Check a voice-isolated render through the next attack.  Keep the performed steps in the master; if a separate reading copy stacks them as a chord, label it as a reduction of one voice, not simultaneous SID notes.

When voices appear to drift apart, compare their actual onset intervals in calls or cycles.  Two voices sharing the same interrupt clock may use different integer countdowns.  Check an early and a late alignment before changing the tempo map or inserting rests.  Preserve the measured offset in the performance export; a regularized beat grid belongs in a separate editorial copy.

### When a rendered MIDI note sounds flat or sharp

Start at the listener's timestamp.  Isolate the suspect voice and compare three things in the same sounding window: the native SID audio, the exported MIDI key plus its active pitch bend and bend range, and the audio rendered from that MIDI with the delivery synth and SoundFont.  Use several short windows if the note has vibrato; one low point is not its center pitch.  Use the native performance as the tuning reference, not the nearest equal-tempered key.  In a full mix, the strongest peak can belong to a different voice or a harmonic.

If the MIDI agrees with the SID but its render does not, hold the MIDI events fixed and change only the instrument.  A sampled instrument can switch to a detuned sample at a particular key: test the first bad key, another key in that range, and neighboring good keys.  If the error follows the patch, change the program on the affected voice or passage rather than transposing the notes or flattening the source vibrato.  Reopen the MIDI to verify that only program changes differ, then measure the same notes in the new render.  Report the timbre tradeoff and name the tested sound bank; the result need not apply to other synths.

For listening review, offer **SID** and **MIDI** controls on a shared timeline.  Render the delivered MIDI, keep both files aligned to the same musical origin (including lead-in), and let the listener switch either way at the current playback position without restarting.  Label both sides and use comparable listening levels without erasing dynamics.  Check a switch late in the piece as well as near the start: an onset offset or a drifting clock can make adjacent notes sound like a pitch error.

### Engrave and check a performance transcription

The [notation guide](notation/README.md) includes a two-staff original example, a callable exporter, and a test that engraves a deliberately shortened note. ## Keep the extraction to the player and the music data

Ship **only the player and the note data it needs to perform the tune**.  Note data includes musical structure the player actually consumes: patterns, order lists, durations, instruments, envelopes, and effects.  Keep RAM snapshots, unrelated game code or graphics, unused address gaps, per-frame replay logs, and verification traces out of the delivered SID.  They can be valuable evidence in a separate working directory.  Prefer the source sequencer and its compact commands to an unrolled recording of register writes.

The file layout need not match the original memory layout.  If the original player and note data occupied separate ranges, concatenate just those ranges in the SID payload.  When fixed addresses matter, include a small init stub that copies **the player and the note data** back to their respective original addresses before calling the player's real init; the SID's play entry then calls or points to the restored player.  Leave out the unrelated bytes that originally sat between the ranges.  If both already work at their load addresses, no copy is needed.

List the packed source, runtime destination, and length of each move.  Check copy order and overlap so the stub does not overwrite itself or any still-needed source.  Document scratch space and peak RAM, including any temporarily live duplicate, and keep the host driver out of all destination ranges.  Verify repeat init, play, and a loop **after the moves** with the declared banking.  A smaller file need not use less runtime RAM.  Report header, player, and music-data bytes separately.  PSID `startPage`/`pageLength` describe room for the **host driver**, not where init should copy the tune.  Do not claim a clean `0/0` header if init writes outside the loaded image within the driver ranges; the writer defaults to clean images and optionally accepts declared dirty pages.  The [Two Hops example](examples/two-hops/README.md) ships a 73-byte player adjacent to a four-byte table and copies both into place on each init.

## Make an executable SID file

**Selecting a song to extract:** The [read-only song selector](selection/README.md) accepts fixed PSID headers from v1 through v4 without admitting them to the writer below.  Request the 1-based song from the host; an ordinary PSID init receives **song minus one** in A.  Read `startSong` rather than assuming it is 1.  A CIA speed bit specifies a source, not the final timer rate.  Capture two fresh selections and compare an early pitch or gate plus the matching audio before labeling a multitrack release.

[`sidfile.py`](sidfile.py) is a dependency-free Python 3.8+ **container reader/writer**, not an assembler, emulator, register-dump converter, or TED player.  Supply already linked 6502/6510 code and data for a C64 player, with working init and play subroutines.  To start from a trace, first implement a timed replay driver or reconstruct the musical sequencer, allocate RAM, link at the intended address, and validate actual playback.  Prepending `PSID` to writes or changing the magic to `RSID` cannot do this.

The contract is deliberately narrower than the [HVSC SID file format specification](https://www.hvsc.c64.org/download/C64Music/DOCUMENTS/SID_file_format.txt) (revision reviewed: 2026-10-09):

| Field | Accepted profile |
|---|---|
| Format | `PSID` v2NG, version 2, big-endian header fields, fixed data offset `$007C`; one SID at `$D400`, one song, start song 1. |
| Load | Contiguous, nonempty raw payload entirely in `$0400` through `$9FFF`.  Default header load 0 places the effective load address in a two-byte **little-endian prefix**, not loaded into RAM.  With explicit nonzero header load, payload starts directly at `$007C`.  Pass raw linked bytes with **no PRG prefix** to the API in both cases. |
| Calls | Explicit nonzero init and play entries inside the payload.  Select the sole song with A=0 for init.  Both return via RTS; the host calls play at the specified cadence, using `$01=$37` before each call for these addresses.  No implicit init, IRQ-only play=0, external MUS, or PlaySID-specific environment. |
| Speed and clock | Explicit PAL or NTSC.  Speed 0 = video-frame cadence; speed 1 = CIA 1 timer A, nominal default 60 Hz unless reprogrammed.  The flag is **not a timer period**; document and observe any custom latch/counter mode and changes.  The header does not retune a payload. |
| Flags and text | SID model `unknown`, `6581`, `8580`, or `both`.  Other features and reserved fields clear.  Three Windows-1252 fields of at most 32 bytes each, canonically zero-padded; full 32-byte fields have no terminator. |
| Relocation | `startPage=pageLength=0` declares a clean payload: no writes outside its loaded data range **within the driver ranges**.  These fields describe space for the host driver, not relocation of the tune.  For separately copied ranges, the optional `dirty_pages` API computes the largest free driver range in the supported banking profile.  The CLI remains clean-only.  A caller must establish actual memory use, entry validity, and timing from code or execution, not by parsing the header. |

Versions 1, 3, 4, and 5, multi-SID, multi-song, unknown/either clock, noncanonical padding, surplus speed bits, undeclared or mismatched relocation ranges, and `RSID` are refused, not silently normalized.  Some rejected PSIDs are perfectly valid outside this profile.  RSID requires a real-C64-style environment; its header load, play, and speed fields must be zero, with a prefixed effective load address and different startup/IRQ obligations.  Use a suitable RSID-aware player instead.  For a BASIC-flagged RSID, the zero init field means execute the BASIC program, not `JSR` to zero or to its load address.  Check the linked BASIC lines, the launch environment, and a SID gate store reached through the stock `POKE` handler before assigning the tune a play routine.  A BASIC `GOSUB` and delay loop can schedule the notes without a machine-code callback.  Try both songs of [Turnstile](examples/turnstile/README.md): the BASIC RSID host supplies the zero-based song number at `$030C`, and the nine-line player reads it with `PEEK(780)` to choose which phrase starts.  If both selections sound alike, check that byte before changing the score.

**Callable API:** `write_psid(t: Tune, *, dirty_pages=()) -> bytes` and `read_psid(data: bytes, *, dirty_pages=()) -> Tune`.  `Tune` is immutable; addresses are effective addresses, `payload` excludes the optional prefix, and `prefix` preserves which load form was used.  Supported wire images round-trip byte-for-byte.  Unsupported input raises `ValueError`.  The CLI creates new files only; `inspect --payload-out` writes the raw linked bytes, not a PRG.

```python
from pathlib import Path
from sidfile import read_psid, write_psid

wire = Path('examples/glass-steps.sid').read_bytes()
t = read_psid(wire)
assert (t.load, t.init, t.play) == (0x1000, 0x1000, 0x1003)
assert write_psid(t) == wire
```

### Build and check the original tune

Run from this skill directory.  Only rebuilding needs cc65 (`ca65`, `ld65`).  The supplied `.sid` is ready to play.  Use a new output directory so inputs stay untouched.

```sh
out=$(mktemp -d)
ca65 examples/glass-steps.s -o "$out/demo.o"
ld65 -t none -S 0x1000 "$out/demo.o" -o "$out/demo.bin"
python3 -B sidfile.py pack "$out/demo.bin" "$out/demo.sid" --load 0x1000 --init 0x1000 --play 0x1003 --clock NTSC --rate vbi --model 8580 --name 'Glass Steps' --author 'Original example' --released '2026'
cmp examples/glass-steps.sid "$out/demo.sid"
python3 -B sidfile.py inspect "$out/demo.sid" --payload-out "$out/unwrapped.bin"
cmp "$out/demo.bin" "$out/unwrapped.bin"
python3 -B tests/test_sidfile.py -v
python3 -B tests/check_player.py -v                 # optional dependency: py65 1.2.0
sidplayfp -m -t3 -w"$out/demo.wav" "$out/demo.sid"
python3 -B tests/check_render.py "$out/demo.wav"     # mono 16-bit PCM
```

The independent header test uses field offsets, not the implementation’s pack format.  The CPU test directly calls the shipped bytes and checks the actual SID writes for two loops plus the seam; removing the gate bit must fail even though the header still parses.  The render test checks the four expected fundamentals in eight sustained windows.  None of these is a blanket SID compatibility or physical-hardware test.
