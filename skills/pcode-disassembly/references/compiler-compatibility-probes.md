# Using a compatibility suite without mistaking it for a decompiler oracle

Use a suite when a plausible BASIC listing could be wrong in a way a byte count or token round trip would miss.  The [pinned BASIC V2 Compatibility Suite](https://github.com/EgonOlsen71/compsuite/tree/587bd9cecb76ff027cafd05e7ad831eec129c397) supplies a source, multiple compiled objects, and an author's [results table](https://github.com/EgonOlsen71/compsuite/blob/587bd9cecb76ff027cafd05e7ad831eec129c397/results.md).  They answer **different** questions.  No suite, external tool, or download is needed for ordinary reconstruction.

1. Identify each object independently of its filename.  Verify revision, output mode, layout, and instruction boundaries.  A recognized runtime in a native output is not permission to decode its payload as p-code.  Also check whether a purported new sample is byte-identical to a previous one.
2. Reconstruct from the binary alone.  Separately read the source, including setup, shared variables, the oracle, and expected DATA.  Only then align the two.  Map an effect back to its instruction address, not merely to a similar source line.
3. Keep four columns distinct: **stock language behavior; instructions the compiler emitted; listing the decompiler produced; observed behavior of the exact executable**.  An upstream run goes in its own attributed column.  Matching the source spelling is not always desirable.
4. Audit the tester.  Here the error flag resets before each case; the final banner tests the last flag, not an aggregate.  The IRQ watchdog writes a screen warning after 200 ticks and chains to the old handler.  It neither exits the loop nor proves the current test terminated.  Record per-case results and noncompletion separately, with a bounded stop for any authorized run.
5. Check *what the oracle can distinguish*.  The shared vector checker reads through its inclusive upper index, clears each result slot, and advances the global DATA cursor.  A prior case can disturb a later one.  Here the checker also starts its own `FOR i` and leaves `i=cm%+1`; it could mask an incorrectly retained frame.  When designing a control, use an independent loop variable and prefill result slots with a value different from the expected result.  A passing value with one chosen input does not establish operand order, effect count, error behavior, or inverse uniqueness.

### What to challenge in the 17 cases

| Case(s) | Discriminating question |
|---|---|
| Array initialization | Were integer and floating arrays checked **before** explicit zeroing?  An allocation, an implicit zero, and a store of zero are different evidence. |
| Four arithmetic cases | Separate evaluation precision from assignment conversion.  `5000+30000-32000` gives 3000 both with wide arithmetic and with 16-bit wrap at each operation.  Neither the floating nor integer destination in those two cases distinguishes wrapping.  An intermediate product can also exceed signed 16-bit even when the final result fits.  In the PETSpeed object the source's multiply-then-divide is emitted as division **before** multiplication.  For the chosen inputs both yield 1562.5; that agreement does not recover the original expression tree.  Preserve the emitted grouping and distinguish the 1562 integer destination. |
| Random numbers | An overwritten result need not be a dead operation.  Preserve reseed, advance, argument signs, order, and destination.  Two RND calls can still be two *wrong* calls.  For this sequence the stock oracle differs if the reseed is deleted or a draw duplicated; see the [exact ROM vectors](../../c64-basic-v2-rnd-analysis/SKILL.md#checking-a-compilers-random-call-sequence).  A compiled runtime is not necessarily the stock ROM. |
| Two Boolean cases | A comparison used as a number is 0 or −1 under stock BASIC, not 0 or 1.  Distinguish this from 16-bit bitwise AND/OR in an address or byte mask, and retain the sequence of POKE/PEEK operations. |
| Zero-step exit | The loop body writes its own control variable on iteration 50.  Keep the explicit zero step and the write; do not unconditionally label it an infinite loop or replace its test with a host-language loop condition. |
| Six nonlexical FOR/NEXT cases | Check, separately: a computed branch to two bare NEXT sites; a jump back into an earlier loop body; a single NEXT reached with different control variables; reusing an active variable in nested flow; five distinct NEXT entries selected by one ON GOTO; and RETURN from inside a subroutine's loop while its caller has a live loop.  Recover target order, entry contexts, repeat edges, and exit edges before introducing a structured loop.  If the frame is unknown, leave a bare NEXT and label the gap rather than pairing by proximity. |
| Two-dimensional array | Check the dimensions and strides with distinct values at independent coordinates.  Here the five reads all resolve to `a(3,4)`; passing does not determine the array layout.  A flattened index split by quotient/remainder may yield the right coordinates but duplicate a read or call.  Preserve the original number of observable evaluations.  Five identical expected values alone do not identify a unique subscript expression. |
| DATA access | Compare raw retained field spellings separately from numeric READ conversions.  Here the five fields `0,,.,e,` are checked against five numeric zeros, after five result slots are first filled with a nonzero sentinel.  Preserving the expected zeros is not a substitute for preserving the empty fields, delimiters, and cursor. |

### An `ON` target-order error the original loop cannot see

In [FOR 5](https://github.com/EgonOlsen71/compsuite/blob/587bd9cecb76ff027cafd05e7ad831eec129c397/src/compsuite.bas#L131-L142), the five bare `NEXT` sites in physical order are visited as **1, 2, 4, 3, 5**.  Sorting the table changes two destinations but not the checked cells: the selector is stored *before* dispatch.  All continuing sites resume the same body, and the last site still falls through to the same exit.  The saved BASIC-64 table actually preserves the nonsorted order; sorting is a negative control, not a reported compiler bug.

To distinguish all 24 permutations that keep the last site fixed, use a new authored probe with the same transfer and put `T=10*T+digit` immediately before each `NEXT`.  The digit belongs to the destination, not the selector.  With `T=0` initially, the intended order predicts `12435`; the sorted order predicts `12345`.  Use an ordinary numeric variable, not a signed 16-bit `%` accumulator.  Moving the *final* target can change exhaustion fallthrough too.  Compare an ordered list, not just its set of CFG successors.

### Disk labels, runtime identity, and usable payloads

The suite disk has ten compiled entries.  Two BASIC-64 entries share the same 5,528-byte runtime prefix.  At `$2018`, one has the expected bridge into p-code; the other starts `LDA #$20 / STA $47`.  The latter supports identifying a runtime and a native entry, **not** using the p-code reader on the rest of the file or classifying every later byte as native.  Only three of the ten were admitted by the strict readers here: BASIC-64 p-code, BLITZ, and PETSpeed.  The PETSpeed suite object also appears in the PETSpeed decompiler's examples; count it once, not as independent validation.

Two binary checks make the differences concrete.  In the admitted BASIC-64 object the sequence at `$2320` is integer multiply, convert an operand to floating point, then floating divide; the PETSpeed example above divides first.  In the BASIC-64 integer-destination case, conversion happens **after** the 16-bit product: 50000 wraps to −15536, so the following division by 32 cannot recover 1562.5.  This explains how the reported overflow failure can occur, without purporting to measure the final stored value.  Do not transfer an expression tree from one build to another.  In the BASIC-64 DATA region, all 204 fields match the source stream (allowing the source's lowercase `e` to be stored as `E`), including its two empty numeric-input fields.  That is a check on the stored data, not on what the runtime returns from READ.

### A real disagreement: the calls survived, but the seed changed

Binary-only readings of the admitted BASIC-64 p-code, BLITZ, and PETSpeed examples all retain `RND(-7)`, then `RND(1)`, with both results assigned to the same variable.  The numbered PETSpeed export does too.  The upstream table reports a PETSpeed failure: before blaming a missing call, check the runtime's *argument representation*.

In the pinned PETSpeed `$2267` revision, the integer literal handler writes `$FF/$F9` into `$64/$65` for −7.  The RND handler at `$1747` branches by type.  On the integer path it computes the sign and calls ROM `$E09A`, bypassing the ordinary floating sign test without converting the argument into a floating accumulator.  The negative ROM arm reverses the four mantissa bytes: its leading pair is now `F9 FF`, independent of the two unspecified bytes.  Normalization and rounding cannot give the stock −7 seed exponent `$68`; the integer path gives `$80`.  This is a static distinction supported by isolated stock-ROM controls, not a replay of the compiled suite or a measurement of its next draw.  The listing correctly recovers the calls; re-running that listing under BASIC is a different experiment.  The portable `SemanticTests.test_overwritten_rnd_result_preserves_both_calls_in_order` regression checks both ordered calls and both stores across the three instruction families, without requiring any suite object.

**Stop criterion:** when source and reading differ, find the first layer where they differ.  A wrong listing warrants a lifter fix and a regression.  An already-different binary warrants documentation of what it does, not a change to make the listing resemble the source.  If the dispute is about runtime behavior and only static evidence is available, record it as untested.
